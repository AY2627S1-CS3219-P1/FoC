# Preserve on-time delivery submissions through delayed validation

The approved receipt-time contract supersedes the earlier final-processing-time deadline. A valid confirmation durably server-received strictly before pickup plus twice the delivery duration remains eligible after processing delay. PostgreSQL `clock_timestamp()` after the parent Order lock supplies the receipt time. The same clock and lock govern timeout, admission, rejection and finalization. Phone time, selected photos and an upload alone do not reserve eligibility. See [shared delivery terms](../../glossary.md).

The courier uploads and successfully calls `VerifyProofUpload` before submitting confirmation. That first successful server verification records immutable preexistence evidence. Admission freezes the normalized proof IDs and handover/outage choice in one pending receipt, then commits before inspecting storage again. Already-verified proof may therefore enter pending when confirmation inspection is unavailable, but an unverified identity or later replacement cannot inherit an old receipt. This preserves the existing upload/check/confirm flow without trusting a client completion claim or S3's coarse creation timestamp.

Storage and decoding stay outside the parent transaction. Unknown inspection retains pending with database-clock backoff and a prolonged-failure alert. Invalid proof rejects that submission, allowing a new valid submission only before the original deadline. Cancellation can win the same parent lock and supersedes pending work. An accepted receipt and proof attachment commit with the Order revision, audit and outbox. Effective `DeliveredAt` is the receipt time; `UpdatedAt`, processing and audit time remain separate. Accepted identical replay survives subsequent lifecycle changes.

An outage exception requires repeated explicit server PUT-service failures, not authentication, configuration, signing or transport errors. Certification is scoped to the actual upload route, has bounded validity and is locked against revocation during admission. Once validly admitted, the immutable outage evidence remains eligible through recovery or a later route change. A missing authority fails closed. Stored-byte identity is separate from browser-route signing identity, so changing the public hostname rotates grants and outage certification without changing the proof ID.

The runtime uses the SDK's fixed signing-time hook and a credential/endpoint epoch, never stored bearer URLs. Expiry or credential rotation refreshes the generation, not the proof identity. Twenty active staged identities and 200 new identities per order/courier/hour bound staging and unknown-identity fences. Known retries/removal remain available at the new-identity budget. Retired keys are revisited after grant expiry because an in-flight PUT can finish after the first deletion. This cleanup never deletes accepted evidence. Report/appeal-dependent retention and revocation-safe nonparticipant admin access remain the explicitly deferred dependencies, not part of this receipt mechanism.
