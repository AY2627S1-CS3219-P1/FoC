- Communication: synchronous (CRUD on review should be fast)
- Model:
  - Review { id: UUID, reviewer_id: UUID, reviewee_id: UUID, order\_id: UUID, rating: int\[1, 5\], comment: string\[100000\], created\_at: timestamptz, deleted\_at: timestamptz }
  - ReviewRemoval { id: UUID (surrogate), review\_id: UUID (UNIQUE FK \u2192 reviews(id)), reviewer_id: UUID, reviewee_id: UUID, order\_id: UUID, reason: string, created\_at: timestamptz, created\_by: UUID }
  - User { …, reviewCount: int, avgRating: float64 }
  - Notes:
    - `order_id` has no foreign key (the Order Service owns orders); it is validated at submission time via `OrderInternalService.GetOrderParticipants` -- the order must exist, be `Completed`, and have exactly the caller and reviewee as its participants. Validation **fails closed**: when the order service is unreachable or unconfigured, submissions are rejected.
    - `reviewer_id` and `reviewee_id` reference `users(id)` and are validated to exist, since the User table is in our domain. A review may not have `reviewer_id == reviewee_id` (no self-review).
    - Removal is a **soft delete**: removing a review marks its `deleted_at` (the `reviews` row is retained for audit) and records a `ReviewRemoval` audit row that references the review via `review_id`. "Reviews that have not been removed" therefore means reviews whose `deleted_at IS NULL`. A surrogate `review_removals.id` primary key is retained (a fresh UUID) as preparation for permanent deletion in a later phase.
    - `User.reviewCount` and `User.avgRating` are derived from the reviewee's non-removed reviews and are written by the sqlc review repository (lock the row, compute `COUNT(*)` / `SUM(rating)`, `UPDATE`) -- not GORM.
- Service Interface:
  - SubmitReview(reviewer_id UUID, reviewee_id UUID, review ReviewSubmission) error
    - ReviewSubmission { rating: int, comment: string }
    - ReviewResponse { id, from, to, orderId: UUID, rating: int, comment: string, created\_at: datetime }
  - ListReviewsForUser(UUID, Pagination) (ReviewPage, error)      // returns a composed ReviewPage (reviews + embedded PageInfo)
  - ListReviewsFromUser(UUID, Pagination) (ReviewPage, error)     // returns a composed ReviewPage (reviews + embedded PageInfo)
    - ReviewPage embeds the shared `pkg/pagination.PageInfo` (page, page_size, total_items, total_pages): `ReviewPage { reviews: Review[], pagination: PageInfo }`.
  - The service composes the page, mirroring supplier-service: it receives a `pkg/pagination.Pagination` that is valid-by-construction and immutable -- the shared model's constructor `pagination.New` normalizes `page`/`page_size` on entry at the handler (or rejects with a sentinel error, which the handler maps to a response code), so there is no per-service normalization -- then fetches the page and `total` from the repository -- the repository runs an indexed COUNT for total_items plus the LIMIT/OFFSET page fetch, returning (reviews, total), and the service sets the embedded `pkg/pagination.PageInfo.total_items`/`total_pages`. `total_pages = ceil(total_items / page_size)`. The handler maps this composed `ReviewPage` to the proto `ReviewPage` (which nests proto `PageInfo`).
  - RemoveReview(id UUID) error
  - ListReviewRemovals() (ReviewRemoval\[\], error)
    - ReviewRemoval { id: UUID, reviewer_id: UUID, reviewee_id: UUID, order\_id: UUID, reason: string\[100000], created\_at: timestamptz, created\_by: UUID }
  - CalculateReviewStatisticForUser(id UUID) (count int, avgRating float64, error) – statistics updated by SubmitReview and RemoveReview
- Dependencies:
  - None
- RPC Interface (handlers)
  - rpc SubmitReview({ from, to, order\_id, rating, comment }) (response {})
  - rpc ListReviewsForUser(ListReviewsForUserRequest) (ReviewPage) // request embeds an optional `Pagination` (from the shared pagination.v1 package); response is a `ReviewPage` that nests `PageInfo`. Lists reviews received BY a user (reviewee); the suspended self-target ABAC rule is enforced in the handler.

Request embeds an optional `Pagination` (from the shared pagination.v1 package); response is a `ReviewPage` that nests `PageInfo`. The underlying ListReviewsFromUser method may later be exposed as a public ListReviewsFromUser(user_id) RPC, which reintroduces ABAC (see authorization constraints above).

  - rpc ListReviewRemovals() (removals { removals: ReviewRemoval\[\] })

- Constraints:
  - A review comment and removal reason must not be empty, and should be at most 100000 characters.
  - There must be a unique constraint that there can only be one review for a specific user_id and order_id
  - IDs should use UUIDv7, in preparation for migration to UUIDv7 (check yihao's Github PR)
  - Authorization matches the RBAC/ABAC nature of each rule, following supplier-service's colocated, token-claim interceptor:
    - **RBAC in the interceptor.** A colocated Connect interceptor after authentication uses token claims (the `Caller` in context) with an `authorizeCaller(caller, procedure)` switch -- no per-request database lookup and no access to the request message. `SubmitReview` is non-suspended users only; `RemoveReview` and `ListReviewRemovals` are admin or super admin only; `ListMyReviews` and `ListReviewsForUser` allow any authenticated user (no RBAC gate).
    - **ABAC in the handler.** The suspended-user target rule for `ListReviewsForUser` is enforced by a small private function owned by the handler: if the caller is suspended, the requested `user_id` must equal the caller's own ID. Kept in the handler because it compares the request target to the actor, and the ABAC need is low.
  - Token-claim authority is intentional; Redis-based access-token revocation will later reconcile claim divergence from role changes.
  - Future extension `ListReviewsFromUser(user_id)` (exposing the `ListReviewsFromUser` service method as an RPC) -- admin always, otherwise only the caller's own `user_id` -- splits the same way (RBAC/ABAC) and is not implemented now.
  - The unique "one review per (user_id, order_id)" rule is enforced with **two** unique indexes -- `UNIQUE (reviewer_id, order_id)` and `UNIQUE (reviewee_id, order_id)` -- so a participant can give and receive at most one review per request.
  - `order_id` is validated via the order service's internal `GetOrderParticipants` RPC (no FK; the Order Service owns orders). The order must be `Completed` with exactly the two callers as participants; the call fails closed when the order service is unavailable or `ORDER_SERVICE_URL` is unset. Participant IDs (`reviewer_id` / `reviewee_id`) are validated to exist in the User table; a review may not have `reviewer_id == reviewee_id`. Removing a review records a non-empty `reason` (R4.2).
  - IDs are generated as UUIDv7 in Go (`uuid.NewV7()`). The DB default (`gen_random_uuid()`) is left unchanged and switched to UUIDv7 only once yihao's system-wide migration lands (Postgres 18 has no native `uuid_v7()`).
  - A user's `reviewCount` / `avgRating` are updated by the sqlc review repository on submit and remove.

- Performance:
  - There is a need to calculate a user's aggregate rating and review count whenever a review about that user is created or removed. Reviews are indexed by `reviewer_id` and `reviewee_id`; indexing has made aggregation fast enough that recalculation runs **synchronously**.
  - The recalculation runs **synchronously inside the same transaction** as the review create/delete -- not in a separate goroutine. The RPC therefore creates or deletes the review and recomputes the user's stats atomically: the stats are updated before the RPC returns.
    - Recalculation first locks the user's row (`SELECT ... FOR UPDATE` on `users`), then reads `COUNT(*)` and `SUM(rating)` in a **separate statement** after the lock is held -- a locking query must not also read the aggregate, or it may return a stale snapshot (see `LANDMINES/locked-row-relationship-snapshots.md`). Holding the lock across lock -> aggregate -> update makes concurrent submits/removes about the same reviewee converge without races.
  - Listing reviews is paginated with a **shared `pkg/pagination` package** for the whole project -- every future offset-paginated list endpoint uses it. It owns two types:
    - **`Pagination` (request)**: carries `page` and `page_size`. Normalization is owned entirely by the constructor -- `pagination.New(page, page_size) (Pagination, error)` -- as the single project-wide source of truth: it coerces the defaults (page 0 -> 1, page_size 0 -> 20) and bounds (page_size maximum 100), and rejects an unsafe offset (overflow) with a sentinel error rather than exposing a manual `Normalize()` method. Offset is a method on the value (`p.Offset()`), and there is no way to hold an invalid `Pagination`: it is valid by construction. The fields are unexported and the value exposes only accessor methods (`Page()`, `PageSize()`, `Offset()`) -- immutable, so external packages can build it only via `New` (never via a struct literal, and never mutated in place) and copies are race-free. The handler calls `New` on entry and maps the sentinel error to a response code -- not via per-service `normalizeList` helpers -- so every offset-paginated endpoint behaves identically.
    - **`PageInfo` (response)**: carries `page`, `page_size`, `total_items`, `total_pages`. It is a plain holder built by the service -- `total_items` comes from an indexed `COUNT(*)`, and `total_pages = ceil(total_items / page_size)`. It never carries request input, so a request `Pagination` is never polluted with null totals. It is immutable as well -- unexported fields + accessor methods, consistent with `Pagination` -- so the service builds it through a constructor rather than a mutable struct literal. See the Service Interface section.
    - `page` and `offset` are a bijection given `page_size`, so `page` is the canonical wire field (following supplier-service) and `offset` is computed server-side -- `page` and `offset` are never both transmitted.

- Proto contract (`proto/user/review/v1/review.proto`, package `user.review.v1`):
  - Pagination lives in a **project-wide shared package** `proto/pagination/v1/pagination.proto` (package `pagination.v1`), defined once and embedded wherever needed -- not in this service and not in supplier's `shared_types.proto` (which would couple the two services). It defines `Pagination { page, page_size }` (request) and `PageInfo { page, page_size, total_items, total_pages }` (response).
  - Embedding is at the proto level: list requests embed an `optional Pagination pagination` (the `optional` keyword gives presence detection); list responses nest `PageInfo pagination` inside `ReviewPage { reviews[], PageInfo pagination }`. Proto message composition is the embedding mechanism -- Buf generates the Go types (`paginationv1.Pagination`, `paginationv1.PageInfo`), which the handler maps to/from the domain `pkg/pagination` types. On entry the handler constructs `pkg/pagination.Pagination` via `pagination.New(protoPagination)`, which normalizes `page`/`page_size` or rejects with a sentinel error (mapped to a response code) -- there is no standalone normalization, so the value is valid by construction. Because both domain types are immutable, the mapping surface is the accessor methods (`Page()`, `PageSize()`, `Offset()`) rather than exported fields.
  - `PageInfo` is the offset-pagination contract; cursor-paginated endpoints (out of scope here) use a separate response shape and do not embed `PageInfo`.
  - `RemoveReviewRequest` carries both `id` and `reason` (R4.2). Generated with `make buf-lint` and `make buf-generate` (commit contract + generated output together).

- Implementation:
  - Use sqlc: it has been decided that any further new functionality required by user service will utilise sqlc instead of gorm
  - Follow the branch iz/feat/add-admin-allowed-domain-mgt in terms of structuring the code.
    - We should organise the code by the subdomain of this user domain: that is, the whole stack from domain model, repository interface, rpc handlers, concrete service (logic), sql queries-based repository implementation should all be in one folder (for reviews: `user-service/internal/review/`).
  - Recalculation is synchronous: the review create/delete and the user's `reviewCount` / `avgRating` update run in one transaction and return atomically.
  - Recalculation locks the `users` row and reads the aggregate in a separate statement after the lock (see `LANDMINES/locked-row-relationship-snapshots.md`).
  - The sqlc review repository owns the write to `users.review_count` / `users.avg_rating`; GORM does not touch those columns.
  - Frontend side: generated TypeScript only (no review UI components) unless a UI is later decided.
